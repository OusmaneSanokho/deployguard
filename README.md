# DeployGuard

**A secure AWS deployment platform, provisioned entirely with Terraform. It builds, ships, and automatically rolls back a containerized application, with zero long lived AWS credentials anywhere in the pipeline.**

## What this project is, in plain terms

DeployGuard is not a web app. It is the infrastructure and delivery system that gets a small web application into production on AWS safely, and keeps it running correctly.

If you have no cloud background at all, here is the short version: this project builds a private, secured space inside Amazon Web Services, puts a small application inside it, sets up an automatic pipeline that tests and deploys code changes, watches the application continuously, and can recover automatically if a deployment goes wrong. Every part of it was built from scratch using code, a practice called Infrastructure as Code, rather than by manually clicking through AWS's web console. That matters because code can be reviewed, versioned, tested, destroyed, and rebuilt identically at any time. Manual configuration cannot.

## Why this project exists

Most student portfolio projects prove you can build an application. This one proves a different, complementary skill: given a working application, I can build the infrastructure and delivery system that gets it into production securely, observes it while running, and recovers it automatically when something breaks.

**Engineering narrative:** Provision -> Secure -> Deploy -> Validate -> Observe -> Detect Failure -> Rollback -> Reproduce

This is the third project in a three part portfolio:

1. **CloudRescue** taught monitoring and automated recovery of a running system, on EC2 with Docker Compose.
2. **AI Internship Copilot** taught building and deploying a full stack AI application, on Next.js and Supabase.
3. **DeployGuard**, this project, teaches building the infrastructure and delivery pipeline that lets an application be deployed safely in the first place.

Every part of this repository is real, live infrastructure. It was provisioned, deliberately broken five separate times, debugged, and recovered using the real AWS console, the AWS CLI, and CloudWatch Logs. Nothing here is simulated or staged.

    ECS -.->|secrets, image pull, logs| EP
    ECS --> CW

    SNS -->|email| Dev

**No NAT Gateway.** Private subnets have no route to the general internet at all. They can only reach a small, specific set of AWS services through VPC Endpoints, for ECR, CloudWatch Logs, SSM, and S3. This was a deliberate least privilege networking decision, not a cost shortcut, though it also happens to cost roughly the same as a NAT Gateway at this project's scale.

### How a request actually flows through the system

1. A user or `curl` request hits the Application Load Balancer's public DNS name.
2. The ALB checks whether the running container is healthy, using the `/health` endpoint, and forwards the request to it.
3. The container runs inside a private subnet with no direct internet access.
4. If the request needs the database, the container talks to RDS PostgreSQL over a security group rule that only trusts traffic from the container's own security group. Nothing else, including the internet, can reach the database directly.
5. The container's database password was never typed by a human. It was generated by Terraform, stored encrypted in SSM Parameter Store, and injected into the container at startup.

## What's actually implemented

| Layer | Components |
|---|---|
| **Infrastructure as Code** | 100 percent Terraform. VPC, subnets, routing, IAM, compute, data, CI identity. Remote state in S3 with native locking. |
| **Networking** | VPC, 2 public and 2 private subnets across 2 AZs, Internet Gateway, 5 VPC Endpoints, S3 gateway plus ECR and Logs and SSM interface. |
| **Security** | 3 tier Security Group chain, ALB to ECS to RDS, badge based, not CIDR. RDS `publicly_accessible = false`. Least privilege IAM, execution role and task role separately scoped. |
| **Compute** | ECS on Fargate, FastAPI application, Docker, ECR |
| **Data** | RDS PostgreSQL, auto generated password stored in SSM Parameter Store as a SecureString, never hardcoded |
| **Load Balancing** | Application Load Balancer, health check driven target group |
| **CI/CD** | GitHub Actions, separate PR validation and deploy pipelines, GitHub OIDC authentication, no stored AWS keys, ever |
| **Deployment Safety** | ECS deployment circuit breaker with automatic rollback on failed health checks |
| **Observability** | CloudWatch Logs, 2 metric alarms for unhealthy targets and 5xx errors, SNS email notifications |

## Key engineering decisions

| Decision | Why |
|---|---|
| ECS Fargate, not EKS | Full container orchestration without the operational overhead of managing a Kubernetes control plane. Appropriately scoped for the project's timeline and goals. |
| VPC Endpoints, not NAT Gateway | Private subnets stay unreachable from the general internet entirely, not just firewalled. A stronger security posture than a NAT Gateway provides, at a broadly similar cost. |
| SSM Parameter Store, not Secrets Manager | Free tier. Automatic rotation was not needed for this project's scope. |
| Manual `workflow_dispatch` deploy trigger | GitHub's native required reviewers approval gate is Enterprise only for private repos on this plan tier. Manual triggering is the deliberate substitute approval mechanism. |
| HTTP only, no custom domain | No domain was purchased, specifically to avoid the cost. Documented as a known, deliberate limitation, not an oversight. |
| Single-AZ RDS | A cost and complexity trade off appropriate for a portfolio project. Documented, not hidden. |

## Cost design

This project was built with a near zero dollar budget in mind, appropriate for a self funded student project. Cost was treated as a real design constraint throughout, not an afterthought.

**Approximate cost per component if left running continuously, in the us-east-1 region:**

| Component | Approximate cost | Why it's here |
|---|---|---|
| RDS PostgreSQL, db.t4g.micro, single-AZ | About $12 per month | Smallest practical instance size. Single-AZ instead of Multi-AZ to avoid doubling the cost, an acceptable trade off for a portfolio project. |
| Application Load Balancer | About $16 to $22 per month | Required for the public and private subnet security model to function at all. |
| VPC Interface Endpoints, ECR API, ECR DKR, CloudWatch Logs, SSM | About $7 per month each, if run continuously | Replaces a NAT Gateway. Broadly comparable in cost, with a meaningfully stronger security posture. |
| VPC Gateway Endpoint, S3 | Free | Used because ECR stores image data in S3 internally. |
| ECS Fargate, 0.25 vCPU, 0.5GB memory, 1 task | A few cents per hour of actual runtime | Billed only while a task is running, not for idle capacity. |
| ECR, SSM Parameter Store, CloudWatch Logs, SNS | Effectively free at this scale | Well within AWS free tier usage for a low traffic demo. |

**Why VPC Endpoints instead of a NAT Gateway, on cost grounds specifically:** a NAT Gateway costs roughly $32 to $37 per month for an equivalent workload, once its hourly charge and per gigabyte data processing fee are combined. VPC Endpoints cost a broadly similar total amount, but grant access to four specific AWS services only, rather than the entire internet. At this project's scale the cost difference is small. The security difference is not.

**Cost discipline actually practiced, not just claimed:** the full environment, all 44 resources, was deliberately destroyed and rebuilt from Terraform code alone as part of testing, specifically to prove the project can be torn down completely between working sessions and rebuilt on demand, rather than left running and accumulating cost unnecessarily.

**What was intentionally left out to control cost:** no NAT Gateway, no Multi-AZ RDS, no AWS Secrets Manager, no custom domain or HTTPS certificate, no autoscaling, and no always on staging environment separate from the single working environment.

## Real engineering problems solved

These were genuine failures encountered and debugged during development, not staged examples.

- **ECS tasks failed to start** with a timeout error retrieving secrets from SSM. Root cause: the VPC had endpoints for ECR, S3, and Logs, but not SSM. A real gap in the original networking build, invisible until secret injection was actually exercised. Fixed by adding the missing endpoint and forcing a new ECS deployment.
- **ECR authentication failed** with a 400 Bad Request on the standard, AWS documented `docker login` command. Confirmed through research to be a known tooling bug, not a local misconfiguration. Resolved by installing the official Amazon ECR Credential Helper, which authenticates through a different mechanism entirely.
- **GitHub Actions OIDC authentication was rejected** with "not authorized." Rather than guessing, a temporary step was added to decode the real OIDC token and read its actual claims, which revealed GitHub's subject format embeds immutable numeric owner and repository IDs alongside the human readable names. The trust policy was corrected to match the real, confirmed value. This same class of issue recurred later after the GitHub repository was renamed, since the subject format also embeds the repository name, and was resolved the same way: decode the real token, then correct the policy to match.
- **A known, long standing Terraform provider limitation** was discovered while deliberately testing a broken database connection: removing an inline security group rule from Terraform configuration is not reliably detected as a change, a documented issue affecting this exact resource type since 2017. The failure was instead injected directly through the AWS CLI. This is flagged as a reason to migrate this project's security groups to the newer `aws_vpc_security_group_ingress_rule` resource type in the future.
- **IAM permission changes are not always instantly effective everywhere in AWS.** After restoring a deliberately removed IAM permission and immediately forcing a new deployment, two further deployment attempts still failed before a later attempt succeeded, a real demonstration of IAM's eventual consistency rather than a flaw in the fix itself.

## CI/CD pipelines

**PR Checks**, `.github/workflows/pr-checks.yml`, runs on every pull request: `terraform fmt`, `terraform validate`, with no AWS credentials present at all by design, since a PR pipeline should never have cloud access, and a Docker build check.

**Deploy**, `.github/workflows/deploy.yml`, manually triggered: authenticates to AWS through GitHub OIDC with zero stored credentials, builds and pushes the image to ECR tagged with the Git commit SHA for full traceability, updates the ECS service, and waits for the deployment to report genuinely stable before finishing.

## Reliability and failure engineering

All five planned failure scenarios below have been deliberately triggered against the real, live environment, with evidence gathered at each step and the environment fully restored afterward.

| # | Scenario | What was done | What was observed | Result |
|---|---|---|---|---|
| 1 | Bad deploy, automatic rollback | Deployed a version with an intentionally broken health check through the real CI/CD pipeline | The deploy pipeline correctly failed. ECS started two new tasks, both were stopped for failing ALB health checks. The previously healthy task was never interrupted. | Automatic recovery confirmed. No manual intervention needed. |
| 2 | RDS connectivity failure | Removed the security group rule allowing the application to reach the database | `/deployments` failed with a connection timeout after 5 seconds, matching the app's configured timeout. `/health` was unaffected, confirming it has no database dependency by design. | Recovered by restoring the rule through Terraform. |
| 3 | IAM least privilege failure | Removed the ECS execution role's permission to read the database password from SSM | New tasks failed to start at all, with an explicit access denied error naming the exact permission and resource. The already running task was unaffected, since it had already resolved its secret before the permission was removed. | Recovered by restoring the IAM policy through Terraform. |
| 4 | Terraform drift detection | Manually changed a CloudWatch log retention setting directly in the AWS Console | `terraform plan` correctly detected the change and proposed reverting it to match the code. | Recovered with a single `terraform apply`, no manual console correction needed. |
| 5 | Full destroy and recreate | Ran `terraform destroy` against the entire 44 resource environment, then rebuilt it from the same code with `terraform apply`, then redeployed the application through the CI/CD pipeline | The environment came back with genuinely new identifiers throughout, including a new load balancer address and a new database instance. The application was fully functional again once the deploy pipeline ran. | Full reproducibility confirmed from code alone. |

**A genuine limitation surfaced by this testing, documented rather than hidden:** the deploy pipeline currently validates that Terraform code is syntactically correct and that the Docker image builds, but has no automated smoke test that would catch an application level bug, such as a broken health check, before it reaches the live environment. This is a concrete, prioritized item for future work.

## Known limitations and future improvements

Documented honestly, not hidden.

- No automated smoke test runs before a deployment reaches production. A local container health check step in the deploy pipeline, before the image is pushed, would close this gap.
- The RDS security group still uses Terraform's older inline `ingress` block style, which has a documented limitation around detecting removed rules. Migrating to the `aws_vpc_security_group_ingress_rule` resource type would fix this properly.
- No HTTPS or custom domain. The Application Load Balancer serves plain HTTP on its default AWS DNS name. No domain was purchased, specifically to avoid that cost.
- Single-AZ RDS, not Multi-AZ. A deliberate cost and complexity trade off appropriate for a portfolio project, not a production system.
- No automated scaling. The application currently always runs exactly one task. This project's purpose is deployment safety, not elastic scale.
